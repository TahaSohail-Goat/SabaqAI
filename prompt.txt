# PHASE 1: REPOSITORY IDENTIFICATION AND FORCE-SYNCHRONIZATION

## Step 1.1: Identify the repository

Start from the current working directory, wherever you have been launched.

Execute:

```bash
pwd
git rev-parse --show-toplevel
git status
git remote -v
git branch -a
```

Determine:

- The absolute repository root.
- The current checked-out branch.
- The Git remote configuration.
- Whether `origin` exists.
- Whether the repository has a local `main` branch.
- Whether `origin/main` exists.
- Whether uncommitted changes or untracked files exist.
- Whether the repository contains Git submodules or Git worktrees.

Operate on the Git repository associated with the current working directory.

If the current directory is inside a nested directory, navigate to its Git repository root.

Do not accidentally operate on a parent or unrelated repository.

If the current directory is not inside a Git repository, clearly report the issue instead of guessing which repository to modify.

## Step 1.2: Force-synchronize with remote main

**The remote `origin/main` branch is the authoritative source of truth.**

I explicitly authorize you to discard local tracked-file modifications and local commits that are not present on `origin/main` as part of this synchronization.

The objective is to make the checked-out project's tracked files match the latest remote `main` exactly.

First, fetch the latest remote state:

```bash
git fetch origin --prune
```

If a local `main` branch already exists:

```bash
git switch -f main
git reset --hard origin/main
```

If the local `main` branch does not exist but `origin/main` does:

```bash
git switch -C main --track origin/main
git reset --hard origin/main
```

If `main` is checked out in another Git worktree, diagnose and report the situation rather than modifying that worktree or bypassing Git protections.

If the repository uses a detached HEAD, resolve it by switching to the appropriate local `main` branch.

If the remote default branch is not `main`, report this inconsistency instead of silently substituting another branch.

### Critical requirements

- Do not merge.
- Do not rebase.
- Do not create a pull request.
- Do not create a new feature branch.
- Do not retain local tracked changes that conflict with `origin/main`.
- Do not force-push anything.
- Do not modify remote history.
- Do not run `git clean -fdx`.
- Do not delete untracked or ignored files automatically.
- Do not delete local `.env` files, credentials, database dumps, or local development data.

If untracked files obstruct the checkout, identify the exact conflicting paths and stop with an explanation instead of deleting them blindly.

Use the equivalent PowerShell commands where necessary on Windows.

### Step 1.3: Verify synchronization

After synchronization, execute:

```bash
git branch --show-current
git status
git rev-parse HEAD
git rev-parse origin/main
git diff --exit-code HEAD origin/main
```

Confirm:

1. The current branch is `main`.
2. `HEAD` matches `origin/main`.
3. The tracked working tree is clean.
4. The latest remote state has been successfully obtained.

Record the commit hash and synchronization outcome.

If any step fails, report the exact failure. Do not falsely claim synchronization succeeded.

**Do not begin the full project analysis until repository synchronization has been verified.**
